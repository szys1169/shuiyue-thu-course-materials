# 演示与过程管理

本文将课程过程评分细则转成小组的操作清单。课程考勤、成员贡献和 Git 违规由小组按助教安排执行，代码仓库无法替代出勤记录。

## 五分钟功能演示

1. `npm install && npm start`，确认浏览器打开 `http://localhost:3000`，展示可运行状态。
2. 使用 `sakura@hoshi.dev / 123456` 登录，展示会话列表、好友、初始历史消息和个人名片。
3. 使用第二个浏览器窗口登录 `rin@hoshi.dev / 123456`，在两端同一私聊发送消息，演示 WebSocket 实时抵达。
4. 展示历史消息、滚动加载、已读同步、撤回与仅本端删除。
5. 用好友账号创建群聊并邀请成员，在被邀请账号打开邀请箱接受，展示群公告、成员管理、发群消息和退出。
6. 注册一个新账号，展示验证错误提示和新增用户的登录。

## 阶段交付建议

| 阶段 | 建议演示清单 | 交付前检查 |
| --- | --- | --- |
| 第 3-4 周：账户和页面 | 注册、登录、用户资料、基础布局 | 主分支可以从干净环境启动 |
| 第 5-6 周：好友与基础消息 | 搜索/申请好友、私聊发送、会话列表 | 补后端单测并建立覆盖率报告，覆盖率达到 80% |
| 第 7-8 周：群聊和历史 | 创建群、邀请、成员、公告、历史分页 | 两个以上账号演示权限和消息隔离 |
| 第 9-10 周：消息状态 | 已读游标、撤回/删除、未读提示 | 检查重连补拉和数据库持久化 |
| 第 11-12 周：实时与交付 | WebSocket、断线恢复、完整部署演示 | 部署可访问；修复已反馈缺陷；整理说明文档 |

周次仅供计划参考，请以课程实际进度为准。评分细则要求每次指导前提交计划交付功能，并保证已经交付的功能在主分支保持可用。

## 每次助教指导会前核对

- [ ] 记录本周计划交付功能，并逐项按需求文档演示。
- [ ] 确认主分支启动命令、体验账号和演示地址有效。
- [ ] 从空数据库启动一次，确认初始化、外键和演示数据正常。
- [ ] 两个独立浏览器测试实时聊天、群邀请和消息历史。
- [ ] 检查未处理的 SonarQube 告警与上周反馈问题。
- [ ] 后端单测覆盖率至少 80%（第 6 周开始检查）；当前代码首版尚未附测试与 CI 报告，需要小组补齐。
- [ ] 课程要求的指导出勤、请假与小组贡献分工另行登记。

## Git 协作约定

- 使用小粒度功能分支，如 `feature/friend-request`、`fix/message-cursor`，通过 Merge Request 合入主分支。
- Commit Message 建议采用 `feat: add friend request flow`、`fix: preserve message history cursor`、`docs: update demo checklist`。
- 每次提交聚焦一个功能，避免单次改动超过评分细则提示的 500 行；合并后删除功能分支。
- 在至少两名组员之间划分前端、后端、数据模型、文档和测试工作，保留合并记录。
