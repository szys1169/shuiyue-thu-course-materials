# 水月至月生的文档习惯

本页用于攻略、讲义、复习资料、课程说明和其他较长文档。它来自本人署名的 README、复习文档和小班辅导讲义，只保留稳定的写作习惯。

## 文件格式

- README、仓库入口说明和必须在平台直接预览的短说明使用 Markdown 或纯文本。
- 攻略、讲义、复习资料等较完整的文档，默认优先使用 LaTeX；若用户明确指定 Markdown、Word 或其他格式，以当前要求为准。
- LaTeX 文档优先采用简洁的中文 article/ctexart 风格：A4 页面，首页居中放标题、署名和日期，之后写前言，再进入分节正文。
- 数学内容使用规范的定理、定义、公式和分节结构。不要为了显得复杂而堆宏包、装饰色块或花哨模板。
- 新文档需要模仿现有版式时，先查看同类旧文件的首页、标题层级、公式编号和页码，不凭印象重新设计。

## 名称选择

- `水至月生` 用于公开资料的作者署名、文档落款、课程资料共享、正式归属和致谢请求。这是较完整、较正式的作者名。
- `水月` 用于聊天、熟人称呼、较轻松的自我指代、语言风格名称，以及已经以“水月”命名的工具或脚本。
- 正文中不需要反复自称。署名已经明确时，优先使用“我”“本文”或直接省略主语。
- 同一处不要随意混用两个名称。场景从正式署名切换到聊天式说明时才可自然切换。
- 不要仅为了强调目标受众而直接称呼“清华同学”。可以写“同学”“在校学生”“第一次使用的读者”，或直接陈述适用场景；只有内容确实依赖校内渠道时，才客观说明“校内平台”“校园额度”等背景。

## 前言

- 较完整的攻略、讲义和复习资料通常在正文前设置“前言”。README 可以省略。
- 前言先解释为什么写，再说明文档覆盖什么、没有覆盖什么，以及可能存在的不足或更新方式。
- 语气可以比正文稍松，但仍然是完整的书面表达。可以承认资料不完美，也可以邀请读者纠错或来询问。
- 前言最后通常用这一句或非常接近的变体收尾：`如果对你有帮助的话请说谢谢水至月生。`
- 这句话属于个人共享资料的辨识性收尾。替他人写文档、匿名文档或不应出现作者署名的场景不要强行加入。

## Markdown 攻略

- 面向初学者的长篇攻略可以按“前言—名词解释—为什么使用—安装或操作步骤—费用与常见问题—能力边界—相关链接”组织。具体章节可以增减，不要机械套用。
- 文档较长时在前言后设置手写目录。新增、删除或重命名标题后，要同步检查目录文字和锚点。
- 操作步骤使用编号列表；解释、比较和注意事项使用普通段落或项目符号。一个步骤尽量只包含一个主要动作。
- 可以用一小段真实经历解释为什么写这篇攻略，也可以穿插轻微吐槽，但个人经历不应淹没正文。
- 对没有亲自使用过的方案明确说明，不根据二手印象补写体验。对价格、额度、界面和平台政策使用“可能变化”“以实际页面为准”等限定。
- 外部链接标明平台名称、用途和是否属于第三方，不只留下裸链接。文末可以集中列一次相关网址和附件，方便读者重新查找。
- 面向新手时首次出现的 API、API Key、Agent、Skill 等概念应给出一句话解释，并保持英文术语的大小写一致。
- 技术能力之后可以单独讨论使用边界，例如学术诚信、结果验收、隐私和高风险操作。立场应直接，但不要把个人经验写成普遍事实。

## 括号、标点和“喵”

- 括号与句末标点一般不连续出现。避免 `（）。`、`（说明）。`、`）。` 这类收尾。
- 闲聊里可以偶尔用一个右括号放软语气，但不是每段必备特征。
- 正经正文少用括号，优先把必要信息直接写进句子。定义域、缩写、公式条件等技术括注可以正常保留。
- “喵”可以偶尔放在轻松聊天的句尾，也可以出现在明显玩笑式的非正文位置。
- 攻略步骤、课程知识、证明、风险提示、配置说明和其他正经正文不加“喵”。
